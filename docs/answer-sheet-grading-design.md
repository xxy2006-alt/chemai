# ChemAI 答题卡批改系统设计方案

> 2026-07-04 · 基于 Agent 架构的答题卡批量识别+LLM批改+诊断闭环

## 一、产品定位

ChemAI 是 Agent 项目，不是传统 web 工作流系统。答题卡批改功能由独立上传页 + Agent 对话页协同完成。

- **上传页**：批量上传、触发识别、预览进度
- **Agent 对话页**：查进度、触批改、看结果、发诊断
- **不写死工作流**：识别完的数据躺着等审批，老师随时来操作

## 二、技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| OCR 引擎 | MinerU（本地） | 当前使用；生产环境建议替换为百度 OCR（手写体识别更强） |
| LLM 批改 | DeepSeek（已接入） | 语义对比答案，支持方程式/离子式/计算步骤的智能判定 |
| 任务队列 | SQLite + APScheduler | 单机项目，多老师并发用 WAL 模式 + teacher_id 索引隔离 |
| 进度推送 | SSE → Agent 对话页 | Agent 查 `ocr_tasks` 表返回实时进度 |
| 答题卡存储 | 本地文件系统 + DB 索引 | 图片存 `/data/answer_sheets/`，元数据存 `ocr_tasks` 表 |

**为什么不用 Kafka：** 并发量小（几十张/天），SQLite WAL 模式 + APScheduler 轮询完全够用。不加中间件依赖。

## 三、完整流程

```
┌──── ① 批量上传 ──────────────────────────────────────┐
│                                                       │
│  老师打开答题卡上传页                                   │
│  - 拖入或选择多个图片文件（JPG/PNG/PDF，5-10张一批）     │
│  - 预览缩略图，可删除/排序                              │
│  - 每张可标注标题："高一(1)班月考第1张"                  │
│  - 点击"开始识别"                                       │
│                                                       │
└────────────────────┬──────────────────────────────────┘
                     ↓ 写入 ocr_tasks 表（一条=一张答题卡）
┌──── ② OCR 识别 ──────────────────────────────────────┐
│                                                       │
│  APScheduler 后台轮询 pending 任务                     │
│  逐张调用 MinerU OCR：                                  │
│    - 提取学号（如 "202610101"）                        │
│    - 提取姓名（如 "李雨萱"）                            │
│    - 提取每道题的作答内容（ABCD / 填空 / 方程式）        │
│  写入识别结果 JSON 到 ocr_tasks.result                 │
│  状态更新：pending → processing → done/failed          │
│                                                       │
└────────────────────┬──────────────────────────────────┘
                     ↓ 前端进度条实时刷新
┌──── ③ Agent 查进度 ──────────────────────────────────┐
│                                                       │
│  老师在 Agent Chat 里问：                              │
│    "答题卡识别完了吗"                                   │
│    "识别进度怎么样了"                                    │
│                                                       │
│  Agent 调 agent_tool：                                 │
│    query_ocr_progress(teacher_id=xxx)                  │

│    标题1: 已完成 100%                                   │
│    标题2: 已完成 100%                                   │
│    标题3: 处理中 83%                                    │

│  C) 什么都没给                                         │
│     → LLM 自己判断每道题的对错                         │

└────────────────────┬──────────────────────────────────┘

│                                                       │

│  - 不是字符串匹配                                       │
```

## 四、数据库设计

### ocr_tasks 表（新增）

| 字段 | 类型 | 说明 |
|------|------|------|
| task_id | TEXT PK | `ocr_{timestamp}_{file_hash}` |
| teacher_id | TEXT | 上传教师 ID |
| batch_id | TEXT | 批次 ID，同一次上传共享 |
| image_path | TEXT | 图片文件路径 |
| thumbnail_path | TEXT | 缩略图路径 |
| title | TEXT | 老师标注的标题（如"高一(1)班第1张"） |
| student_id | TEXT | OCR 识别出的学号 |
| student_name | TEXT | OCR 识别出的姓名 |
| status | TEXT | `pending` / `processing` / `done` / `failed` |
| progress | INT | 0-100 |
| ocr_result | JSON | 识别出的题目列表 |
| grading_result | JSON | LLM 批改结果 |
| confirmed | BOOL | 老师是否确认 |
| created_at | TEXT | 创建时间 |
| processed_at | TEXT | 完成时间 |

## 五、Agent Tool 设计

新增 3 个 agent tool，加入 `teacher` persona：

| Tool | 功能 |
|------|------|
| `query_ocr_progress` | 查 OCR 识别进度，返回每张答题卡的状态和百分比 |
| `grade_answer_sheets` | 触发 LLM 批改，返回逐学生结果卡片 |
| `save_grading_results` | 批量保存批改结果到 DB，触发诊断 |

## 六、分批次上传策略

- **每批 5-10 张**：避免单次上传过大
- **批次独立**：每批有独立的 `batch_id`，互不干扰
- **多老师并发**：`teacher_id` 索引隔离
- **断点续传**：失败的任务留在 DB，可单独重试

## 七、与现有系统的对接

| 现有模块 | 对接方式 |
|---------|---------|
| 考试工作台 | 如果答题卡对应题库已有试卷，直接匹配答案 |
| 诊断系统 | 批改保存后自动触发 LLM barrier 诊断 |
| 学生档案 | 答题记录写入 StudentAnswer，选 barrier 类型 |
| 考试分析 | 批改完成后调 exam-analytics 端点 |
| 练习/错题 | 错题自动进入学生端的 练习 tab 和 错题本 |

## 八、OCR 引擎说明

| 环境 | 引擎 | 说明 |
|------|------|------|
| 当前开发 | MinerU | 本地 Python 库，擅长印刷体 PDF 解析 |
| 生产建议 | 百度 OCR | 手写体识别更强，答题卡场景更适用 |

MinerU 对手写体支持有限。生产环境建议使用百度 OCR 的文字识别 API（通用文字识别/手写文字识别），其对手写 ABCD 选项和数字的识别准确率更高。代码结构已预留 OCR provider 切换接口。
