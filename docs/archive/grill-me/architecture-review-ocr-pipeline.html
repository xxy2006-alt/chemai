1. The Missing State Machine

Strong
app/services/ocr_service.py app/services/document_parse_service.py agent/channel/langgraph_channel.py

The current code has no concept of state — it's a fire-and-forget function call. But the user flow (upload → preview → confirm → process) spans multiple API calls and requires state persistence across steps.

What needs defining:

State What happened What's stored Next action
UPLOADED File received, validated Raw file bytes, filename, mime type → PREVIEWING
PREVIEWING doc_analysis OCR running + preview_text (streaming?) → READY (success) or ERROR
READY Preview shown to user + preview_text, detected_type user picks: import / grade / search
IMPORTING paper_cut_edu_vlm running + task_id (for polling) → IMPORTED or ERROR
IMPORTED Questions extracted + questions[], + enhanced image URL teacher edits → save → DONE
GRADING correct_edu running + task_id, + exam_id → GRADED or ERROR
GRADED Results ready + per-question results, + graded images teacher reviews → save → DONE
DONE Persisted to DB DB record IDs —
ERROR API failed + error message, + retry count retry / fallback / manual

This state machine must live somewhere. Options:

A) In-memory dict keyed by upload_id (simple, lost on restart)

B) SQLite upload_sessions table (survives restart, queryable)

2. Async Polling — Client-Side vs Server-Side

Strong

Problem

Both paper_cut_edu_vlm and correct_edu are async (create_task → poll get_result). Who does the polling?

Current state: Not defined. The test script polls synchronously in a loop — unusable for HTTP requests (would block the FastAPI worker for 15s).

Two Approaches

A) Server polls, client waits
POST /import → server creates task → server polls in background → returns result when done. Client shows spinner.
B) Client polls the server
POST /import → returns task_id immediately → client polls GET /import/{task_id}/status every 2s → server proxies Baidu each time.

Recommendation: B

The server stores {upload_id: {baidu_task_id, status, result}}. The client polls GET /import/{upload_id}/status. The server proxies to Baidu's get_result on each poll. This gives the frontend a progress indicator and avoids long-lived HTTP connections.

4. PDF Multi-Page Strategy

Worth exploring

A 22-page exam PDF creates 22 API calls. For paper_cut_edu_vlm (async, ~10s each), that's ~220 seconds serial. Two strategies:

Strategy How 22-page time Risk
Serial One page at a time: create → poll → next page ~220s Safe, slow
Parallel Fire all 22 create_task at once, poll all in parallel ~15s QPS limit (Baidu QPS=2 for create_task). Needs rate limiting.
Batch of 3 3 concurrent, after each batch completes start next 3 ~75s Respects QPS=2, 4x faster than serial

5. doc_analysis formula_result — Discarded Treasure

Worth exploring

The doc_analysis API returns formula_result (75 LaTeX formulas per page). The VLM returns qus_words (plain text). But the formula LaTeX is more precise than what VLM extracts.

Decision needed: When importing, should we:

A) Use only VLM output (simpler, one source of truth)

B) Merge: VLM for structure + doc_analysis formula_result for precise chemical formulas (better quality, more complex)
