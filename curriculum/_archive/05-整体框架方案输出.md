### 数据库设计的实际取舍

文件：`app/models/database.py`

不用 PostgreSQL 不用 MySQL，用 SQLite。不是因为"简单"，是因为四个硬约束：
1. Windows 单机部署，没有运维人员
2. 用户量 <200 人，数据量 <10MB
3. `chemai.db` 一个文件就能备份/迁移
4. FastAPI 的 SQLAlchemy + SQLite 零配置启动

实际的表结构（14 个表）：

```
accounts          ← 登录认证，role 字段区分 teacher/student/parent
teachers          ← 教师信息
students          ← 学生信息（含 barrier_type JSON 字段，存障碍分布）
classes           ← 班级（一个教师对应多个班级）
teacher_class_subject ← 教师-班级-科目关联
exam_records      ← 考试记录（class_id → 班级 → 学生）
questions         ← 题目（content/answer/analysis/knowledge_points JSON）
student_answers   ← 学生答题记录（is_correct/barrier_type/consecutive_errors）
student_submissions ← 答题卡扫描提交
upload_sessions   ← OCR 上传会话（PDF 文件存 LargeBinary 字段）
question_sets     ← AI 生成的题库集合
schools           ← 学校信息
parents           ← 家长
parent_notifications ← 家长通知
```

`students` 表的关键设计：`barrier_type` 字段是 JSON，存的是 `{concept: 0.3, reading: 0.5, expression: 0.2}`。这不是拍脑袋——来自第三轮访谈的发现："分数差不多的两个学生，可能一个属于第二类，一个属于第三类"。如果只存分数，诊断就失去意义。

### Agent 架构的三次迭代

**v1：pydantic-ai 单轮调用（已废弃）**
- 文件：`agent/provider/` 下的旧文件（已被 langgraph 替代）
- 问题：单轮调用不支持多步骤工具链，出题→审核→保存需要 Agent 自己记得调用三个工具，经常漏

**v2：LangGraph ReAct Agent（已废弃）**
- 文件：`agent/langgraph_agent.py` 的早期版本
- 设计：一个 Agent 拿全部 14 个工具，LLM 自己决定用哪个
- 问题：路由不稳定，"我要出题"有时被路由到 search_expert，有时被路由到 tutor_expert

**v3：Multi-Agent StateGraph（当前方案）**
- 文件：`agent/langgraph_agent.py:426-451`
- 设计：1 个协调器 + 6 个领域子专家

```python
_SUB_AGENT_DEFS = {
    "search_expert":    {"tools": ["web_search", "search_exam_bank"]},
    "exam_expert":      {"tools": ["show_exam_workbench", "save_to_bank"]},
    "diagnosis_expert": {"tools": ["diagnose_barrier", "show_diagnosis", "show_students"]},
    "tutor_expert":     {"tools": ["chemistry_tutor", "simulate_experiment", "balance_equation"]},
    "bank_manager":     {"tools": ["list_banks", "delete_bank"]},
    "browser_expert":   {"tools": ["web_search", "browse_navigate", "browse_read"]},
}
```

路由流程：`用户输入 → Gateway 关键词匹配 → 高置信度直接路由 / 低置信度 LLM 协调器路由 → 子专家执行工具 → 返回结果`

协调器的核心代码在 `agent/gateway.py:245-289`，关键词匹配：

```python
_has_qword = any(kw in text for kw in ["题", "题目", "卷子", "卷"])
_has_gen = any(kw in text for kw in ["出", "生成", "组"])
if _has_qword and _has_gen:
    tools.append("show_exam_workbench")
```

这个简单粗暴的关键词匹配实际效果比 LLM 判断准。因为 LLM 有时会把"出题"理解为 titor_expert 的讲解场景。

### 前端架构的刻意简单

教师端 6 个页面，学生端 7 个页面。不做 SPA，每个页面独立 HTML，内联 CSS/JS。

为什么？
1. 教书匠不是前端工程师，改一个页面不用学 Vue Router
2. 页面间没有共享状态（不需要 Redux）
3. 每个页面 <500 行，小学生都能维护

教师端页面（`frontend/pages/`）：
- `exam-v2.html`：917 行，Vue 3 内联，四个 Tab（出题/题库/真题/考试）
- `students.html`：学生管理
- `teacher.html`：学情面板
- `diagnosis.html`：障碍诊断
- `ocr.html`：答题卡识别

学生端页面（`frontend/m/`）：
- `index.html`：AI 助教对话，SSE 流式
- `practice.html`：练习 + 做题 + 提交
- `wrong.html`：错题本
- `report.html`：我的（含统计 + 菜单）
- `design-v1.html`：视觉原型（React，仅参考）

共享逻辑在 `app.js`（不到 200 行）：`getUser() / api() / TabBar() / Header()`

### SSE 事件流设计

教师端和学生端共用同一套 SSE 事件格式。这是复用的关键——Agent 不管调用方是教师还是学生，都发同样的 SSE 事件，前端各自渲染。

SSE 适配器：`agent/langgraph_sse.py`，把 LangGraph 的 `astream_events` 事件转成 6 种前端事件：

| SSE type | 触发时机 | 前端渲染 |
|----------|---------|---------|
| `route` | 协调器路由到子专家 | 路由卡片 |
| `sub_agent_start` | 子专家开始工作 | 子 Agent 面板展开 |
| `subagent_text` | 子专家流式输出 | 逐字显示 |
| `tool_call` | 工具被调用 | 工具卡片 |
| `tool_result` | 工具返回结果 | 结果展示 |
| `component` | 内联面板指令 | 渲染内联工作台 |

`component` 事件是设计的精髓——它解决了"工具结果只是文本"的问题。当 `show_exam_workbench` 被调用时，它不返回文本，而是返回 `_component: {component: "exam-workbench", params: {...}}`，前端在聊天气泡内渲染完整的出题工作台。出题不需要跳转页面。

### OCR 管线的三层架构

```
PDF 上传
  │
  ├── 预览层 (preview): Baidu OCR doc_analysis → 3s/页 → 快速预览
  │
  ├── 导入层 (import): MinerU pipeline → 45s/页(CPU) → 完整解析
  │   └── 输出: Markdown + JSON + 图片
  │
  └── 结构化层 (structure): LLM → 提取题目/答案/解析/知识点
      └── 存入 questions 表 + JSON 文件
```

预览用 Baidu（快但精度低），正式导入用 MinerU（慢但精度高），两层分工。结构化层在第一版用 LLM 重写 content（导致截断），第二版直接用 MinerU 原始 Markdown 做 content（`reimport_v2.py` 的实现）。
