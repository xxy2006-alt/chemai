# CHEM AI 需求分析与管理

## 1. JTBD 驱动的需求分析框架

ChemAI 采用 JTBD（Jobs-To-Be-Done）作为核心需求分析框架，辅以用户故事（User Story）和验收标准（Acceptance Criteria）。

### 1.1 JTBD 完整矩阵（15 项）

**功能 Job（7 项）—— 用户需要完成的具体任务**

| # | Job | 当前方案 | 耗时 | 优先级 |
|---|-----|---------|------|--------|
| J1 | 考试后获得班级错题分布统计 | Excel 手动统计 | 1-1.5h/次 | P0 |
| J2 | 快速完成 AI 题目安全审核 | 自己重做全部题目 | 30min/次 | P0 |
| J3 | 获得三维分析报告（知识点+陷阱+真题对比）| 凭经验判断 | — | P1 |
| J4 | 生成定制化错题报告（学生版/家长版）| 手动改写三份 | 20min/次 | P1 |
| J5 | 提供虚拟化学实验 | 静态图片 or 放弃 | — | P2 |
| J6 | 识别学生真实障碍类型 | 凭感觉 | — | P1 |
| J7 | 推送自适应练习 | 统一布置 | — | P1 |

**社交 Job（2 项）—— 用户希望如何被他人看待**

| # | Job | 驱动力量 |
|---|-----|---------|
| J8 | 成为"善用工具"的专业形象 | 被同事认可为与时俱进 |
| J9 | 通过推荐工具维护判断力 | 推荐工具 = 推荐自己的判断 |

**情感 Job（3 项）—— 用户希望获得的情感状态**

| # | Job | 驱动力量 |
|---|-----|---------|
| J10 | 给予 90+ 人班级个性化关注 | 减少"力不从心"的疲惫感 |
| J11 | 不在学生面前失去专业权威 | 保护专业尊严 |
| J12 | 不因学习工具感到时间被浪费 | 学习成本 < 实际节省时间 |

**Pain（5 项）、Gain（4 项）** 从略，详见调研报告。

| 功能 | 映射的 JTBD | 验收标准 | 实现状态 |

## 2. 需求优先级管理

### 2.1 P0/P1/P2 分级标准

| 级别 | 定义 | 判定条件 |
|------|------|---------|
| P0 | MVP 必须实现，无此功能产品不可用 | 映射到 P0 级 JTBD 或用户标记为"刚需" ≥80% |
| P1 | MVP 应实现，发布后 1-2 周内补齐 | 映射到 P1 级 JTBD 或用户标记为"需要" ≥60% |
| P2 | 非 MVP 功能，后续迭代实现 | 映射到 P2 级 JTBD 或用户标记为"不需要" ≥50% |

### 2.2 优先级变更记录

| 日期 | 变更 | 原因 |
|------|------|------|
| 2026-04-15 | OCR 管线 P1→P0 | Baidu OCR 识别率不满足要求，影响题库构建 |
| 2026-04-22 | Agent 多专家架构 P2→P1 | 单 Agent 在复杂场景下路由不稳定 |
| 2026-05-15 | 变种真题 P2→P1 | 教导主任提出需求，行政推动升级优先级 |
| 2026-06-15 | 学生端前端 P1→P0 | 教师端功能完整后，学生端成为瓶颈 |

## 3. 需求变更管理

### 3.1 OpenSpec 变更提案流程

ChemAI 采用 OpenSpec 格式管理需求变更。每个变更都是一个独立的 `openspec/changes/{change-name}/` 目录，包含三个文件：

- `proposal.md`：Why / What / Impact
- `design.md`：Context / Goals / Decisions / Risks
- `tasks.md`：分步实现任务清单（带 checkbox）

已有变更提案清单：
```
openspec/changes/
├── multi-agent-architecture    # Agent 重构为 6 子专家
├── inline-exam-workbench       # 内联出题工作台
├── inline-student-list         # 内联学生列表
├── langgraph-migration         # pydantic-ai → LangGraph
├── mineru-pipeline             # OCR 引擎切换
├── gateway-router-refactor     # 路由重构
├── sub-agent-card-ui           # 子 Agent 卡片 UI
├── student-frontend            # 学生移动端重建
└── ...
```

### 3.2 变更评估矩阵

每次需求变更需通过四个维度的评估：

| 维度 | 评估问题 | 评分(1-5) |
|------|---------|----------|
| 用户价值 | 直接影响多少 JTBD？覆盖几个用户？ | |
| 实现成本 | 预估开发时间？是否影响现有功能？ | |
| 技术风险 | 依赖外部 API？是否需要架构改动？ | |
| 时间窗口 | 是否与当前迭代冲突？能否并行开发？ | |

综合评分 ≥3.5/5 的变更优先纳入当前迭代。

## 5. 需求沟通的实际案例

### 案例 1："我要出题"该怎么路由？

用户说"我要出题"，这看起来简单。但实际有三种可能：
1. 用户想用 AI 生成新题目 → `exam_expert` + `show_exam_workbench`
2. 用户想搜索已有的真题 → `search_expert` + `search_exam_bank`
3. 用户想从题库中选题目 → `bank_manager` + `list_banks`

ChemAI 的解决方案：Gateway 关键词匹配优先判断"出"+"题"→ `show_exam_workbench` + `generate_questions`，高置信度直接路由到 exam_expert。如果用户后续说"不是，我要找真题"，子专家完成后 coordinator 检测到 reroute 信号，重新路由。

### 案例 2：为什么"讲题"和"出题"要分开？

教师的自然语言："帮我出一道氧化还原的题讲讲"。这句话同时包含"出题"和"讲解"两个意图。

Gateway 的处理：
1. 先匹配到"出"+"题"→ `show_exam_workbench`（优先级高，因为包含具体功能词）
2. 再匹配到"讲讲"→ `chemistry_tutor`（但只在没有更高优先级匹配时才启用）

最终路由到 exam_expert 先出题，出完后 coordinator 检测到用户可能需要讲解，reroute 到 tutor_expert。

这是 Agent 架构的核心理念：**不是一次路由就完，是多轮对话中持续判断用户意图的变化**。

### 案例 3：教导主任需求 vs 教师需求的冲突

教导主任要"变种题"是为了防作弊（多套等价试卷）。但教师听到"变种题"第一反应是"AI 又要改我的题目了"。

需求沟通中做了一个关键区分：变种题**不改变考查本质**。四条红线（系数/条件/产物/知识点不变）就是这个区分的具体化。这个区分让教师从"抗拒"变成"接受"。

## 6. 需求文档的实际版本演进

PRD 的三个版本：

**v1.0（1 月下旬）**：第一版 PRD，基于第一轮访谈。核心功能定义较粗略，没有具体的验收标准。

**v1.1（2 月中旬）**：基于第二轮访谈的修订版。增加了三维安全审核报告的具体描述、JTBD 映射表、竞争分析。

**v1.1 实现版（3 月初）**：基于第三轮访谈 + 实际开发反馈的最终版。每个功能都有了明确的代码文件映射和验收标准。

从 v1.0 到 v1.1 实现版的核心变化：
- 优先级调整：OCR 管线从 P1 提升到 P0（Baidu 精度不够）
- 新增功能：`chemical_balance` 独立审核工具（教师反馈"零错误是底线"）
- 删除功能：行政上报功能（教师反馈"第一天就绕过去"）
