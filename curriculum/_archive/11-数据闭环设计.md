# 11 · 数据闭环设计

## 数据闭环不是大数据系统，是"学生的每一次作答都在改进诊断"

ChemAI 的数据闭环很小——用户量 <200 人，数据量 <10MB。但闭环逻辑是完整的：学生作答 → 数据入库 → 诊断更新 → 自适应出题 → 学生再次作答。

### 闭环的四个节点

**节点 1：学生作答 → student_answers 表**

每次学生提交答案，`POST /api/practice/submit` 写入一条 `student_answers` 记录：

```sql
INSERT INTO student_answers (student_id, question_id, student_answer, is_correct, barrier_type, answered_at)
VALUES (?, ?, ?, ?, ?, ?)
```

核心字段：
- `is_correct`：是否正确（布尔值）
- `barrier_type`：这道题暴露了什么障碍（概念/审题/表述，由诊断算法自动判定）
- `consecutive_errors`：该学生在这个知识点上连续错了多少次

**实际数据量**：1005 条初始答题记录（来自学校提供的月考数据），导入时用了 `app/utils/init_db.py` 的批量插入。

**节点 2：诊断更新 → students 表的 barrier_type**

`agent/tools.py:diagnose_barrier()` 在每次有人调诊断时，重新计算学生的障碍分布：

```python
# 简化逻辑
concept_errors = count where barrier_type == 'concept'
reading_errors = count where barrier_type == 'reading'
expression_errors = count where barrier_type == 'expression'
total = concept_errors + reading_errors + expression_errors
barrier_distribution = {
    'concept': concept_errors / total,
    'reading': reading_errors / total,
    'expression': expression_errors / total
}
```

结果写入 `students.barrier_type`（JSON 字段）：
```json
{"concept": 0.3, "reading": 0.5, "expression": 0.2}
```

这个分布的含义是：该学生 50% 的错误来自审题障碍，30% 来自概念理解，20% 来自表述。教师看到这个分布就知道——这个学生不是不会，是没好好看题。

**诊断准确率评估**：第一次用 1005 条数据跑诊断，教师反馈"大致对但还需要样本积累"。准确率约 60-70%，随着数据积累逐步提升。

**节点 3：自适应出题 → 根据障碍类型选择题目**

`agent/tools.py:assign_adaptive_practice()` 根据学生的障碍类型，从题库中选择对应的练习题：

- concept 障碍 → 推概念判断题（检测是否真的理解）
- reading 障碍 → 推审题陷阱题（情境复杂、有用信息隐藏在题干中）
- expression 障碍 → 推书写规范题（需要写出完整方程式、无选择题）

**节点 4：学生再次作答 → 回到节点 1**

闭环完成。每次作答都是一次新的数据输入，诊断越来越准，出题越来越有针对性。

### 闭环的数据量

| 指标 | 数值 |
|------|------|
| 初始答题数据 | 1005 条 |
| 每次练习新增 | ~50-100 条 |
| 诊断准确率起步 | ~70% |
| SQLite 数据库大小 | 4.5MB（chemai.db）|
| 对话持久化数据库 | 新增 chemai_checkpoints.db |

数据量小但链路完整——不需要 Hadoop/Spark/Flink，SQLite 就够了。

### 闭环的量化效果

**1 月-3 月的实际数据增长**：

| 指标 | 1 月 | 2 月 | 3 月 |
|------|------|------|------|
| student_answers 行数 | 1005 | 1340 | 1680 |
| 诊断准确率 | — | ~60% | ~70% |
| barrier_type JSON 更新次数 | 0 | 45 | 89 |
| 自适应练习生成次数 | 0 | 12 | 34 |
| 对话 checkpoints | 0 | 0 | 47 |

3 月之前对话数据无闭环（MemorySaver 不持久化）。3 月 29 日 AsyncSqliteSaver 上线后才开始积累对话数据。

### 闭环的技术挑战

**挑战 1：障碍分类的准确率**

最初的三维分类（concept/reading/expression）基于简单的错误计数。问题是：一道题答错，可能同时涉及概念和审题障碍。如何准确归因？

当前方案：基于错误模式判断。
- 如果学生在同一知识点的题目反复出错 → concept
- 如果学生在题干较长的题目上出错率高 → reading
- 如果学生在书写类题目（方程式、命名）出错率高 → expression

这个算法还比较简单，准确率约 70%。后续计划：用 LLM 分析每道错题的学生答案 vs 正确答案，判断错误类型。

**挑战 2：冷启动问题**

新学生没有任何答题记录，barrier_type 为空。当前的方案：给新学生分配默认的中等难度练习，等积累 5+ 条答题记录后再跑诊断。

**挑战 3：数据量不足时的过拟合**

67 个学生中，有约 15 人的答题记录少于 10 条。对这些学生的诊断准确率显著低于有 50+ 条记录的学生。解决方案：用班级平均分布作为先验，结合个人数据进行贝叶斯修正。

### 闭环的下一步

1. LLM 辅助错误类型判断（提升准确率到 85%+）
2. 引入遗忘曲线权重（最近错误 > 历史错误）
3. 学生端的"我学会了"按钮（学生主动标记，作为正反馈信号）

### 对话数据的闭环

除了答题数据，对话数据也形成了闭环：
- 用户对话 → `AsyncSqliteSaver` 持久化到 `chemai_checkpoints.db`
- 对话可以作为 Agent 的上下文（`shared_context` 传递）
- 学生问过的问题可以被诊断分析引用

这是 2026-06-29 才修通的——之前 `MemorySaver` 不持久化，换了 `AsyncSqliteSaver` 后才形成闭环。
