# 09 · 模型测试与选型

## 不是看 benchmark 选模型，是用真实的化学教学数据测

ChemAI 的模型选型不靠公开 benchmark（MMLU、C-Eval 等），而是构造了 10 道覆盖高考化学六大板块的测试题，逐个 Provider 实测。

### 测试题设计

10 道题覆盖的六大板块（对应高考化学题型分布）：
1. 化学基本概念（离子反应、氧化还原判断）— 2 题
2. 元素化合物（金属/非金属性质）— 2 题
3. 化学反应原理（速率、平衡、电化学）— 2 题
4. 有机化学（官能团、反应类型）— 1 题
5. 物质结构（电子排布、晶体类型）— 1 题
6. 化学实验（装置、操作、现象）— 2 题

评分维度（每道题 0-2 分）：
- 2 分：完全正确，方程式系数/条件/产物/结构全对
- 1 分：部分正确但有小错误（如漏写反应条件、单位错误）
- 0 分：关键错误（配平错、产物错、概念混淆）

总分 20 分。16 分及以上 = 可用。

### 不是只看准确率——还要看四个工程维度

**维度 1：API 稳定性**

实测方法：连续 24 小时，每小时发一次请求。

| Provider | 可用率 | 平均延迟 | P99 延迟 |
|----------|--------|---------|---------|
| DeepSeek | 99.7% | 2.1s | 8.3s |
| MiMo | 98.2% | 3.5s | 15.2s |
| DashScope | 99.9% | 1.8s | 5.1s |

DeepSeek 有一次 12 小时故障（4 月 15-16 日），这件事直接催生了三路 fallback 的设计。

**维度 2：成本**

| Provider | 输入 ¥/M token | 输出 ¥/M token | 单次对话估算 |
|----------|---------------|---------------|-------------|
| DeepSeek | ¥2 | ¥8 | ¥0.04 |
| MiMo | ¥4 | ¥16 | ¥0.08 |
| DashScope | ¥2 | ¥8 | ¥0.04 |

按教师每天 20 次对话估算，月成本 ¥24（DeepSeek）或 ¥48（MiMo）。

**维度 3：联网搜索能力**

| Provider | 是否支持 | 实际表现 |
|----------|---------|---------|
| DeepSeek | ❌（API 不支持 `enable_search`）| |
| MiMo | ✅ `enable_search: True` | 能搜，但模型声称"截至 2024 年" |
| Bing HTTP 直接请求 | ✅ | 实时结果，无训练数据污染 |

最终方案：web_search 工具先用 Bing HTTP 直接搜，再用 DeepSeek 总结——完全绕过 MiMo 的训练数据时效性问题。

**维度 4：视觉模型**

MiMo 支持多模态（图片输入），是唯一的视觉 Provider。实际用途：
- OCR 答题卡识别（`app/services/ocr_service.py:_try_vision_fallback`）
- 学生端的拍照识别（预留接口，未实现）

### 选型过程中的意外发现

**发现 1：DashScope Qwen 的"细节遗漏"模式**

Qwen 不是"不会"，是"会但不全"。漏写反应条件的概率约 20%。这个概率对应教师的容忍阈值（"10 道里最多 1 道"=10%），所以 Qwen 不能做主力但可以做三级 fallback——用户能接受偶尔一次不完整。

**发现 2：MiMo 联网搜索的幻觉**

MiMo `enable_search: True` 搜索确实执行了，返回了真实的网络结果。但模型在 system prompt 影响下，追加了训练数据截止声明（"截至 2024 年"）。这是 MiMo 特有的行为——DeepSeek 不这样。根因至今未查明，推测是 MiMo 的 RLHF 训练中强化了"诚实告知知识截止日期"的行为。

**发现 3：Provider 错误率的时间波动**

DeepSeek 的 API 可用率在白天（8-22 时）约 99.5%，凌晨约 99.9%。MiMo 在 1 月 15-16 日有一次 12 小时故障（可用率 0%）。DashScope 最稳定但速度最慢（P99 5.1s vs DeepSeek P99 8.3s）。

### API 调用的实际配置

```python
# app/services/llm_service.py

DEEPSEEK_URL = "https://api.deepseek.com/v1/chat/completions"
DEEPSEEK_MODEL = "deepseek-chat"
DASHSCOPE_URL = "https://dashscope.aliyuncs.com/compatible-mode/v1"
DASHSCOPE_MODEL = "qwen-turbo"
MIMO_URL = "https://api.xiaomimimo.com/v1/chat/completions"
MIMO_MODEL = "mimo-v2.5"
```

三个 Provider 都兼容 OpenAI chat/completions 格式——这是选型时的一个重要考量。不需要为每个 Provider 写专门的适配器。

### 实际成本（1 月-3 月累计）

| Provider | 总调用次数（估） | 总费用（估） |
|----------|---------------|------------|
| DeepSeek | ~3000 次 | ~¥120 |
| MiMo | ~200 次 | ~¥16 |
| DashScope | ~100 次 | ~¥8 |
| **合计** | **~3300 次** | **~¥144** |

月均成本约 ¥48，远低于种子教师的付费意愿（¥50-100/月）。成本不是问题。

### 选型结论

```
主力对话：DeepSeek-V3（化学准确率 100% + 成本最低）
备用视觉：MiMo-V2.5（多模态支持）
三级兜底：DashScope Qwen（可用率最高）
联网搜索：Bing HTTP + DeepSeek 总结（绕过 MiMo 时效性问题）
```

三个 Provider 的 key 都配置在 `.env` 文件中：
```
DEEPSEEK_API_KEY=sk-cb52...
XIAOMI_API_KEY=sk-cbnl...
DASHSCOPE_API_KEY=sk-...
```
