## 项目背景

上两节课你搭好了后端骨架，让 FastAPI 跑了起来。但我们现在面临一个关键问题：**你到底要做什么功能？**

一个常见的错误——也是大多数失败项目的起点——是开发者替用户想需求。"我觉得老师需要这个"、"我觉得学生需要那个"。但开发者不是化学教师，开发者没在 90+ 人的大班教过书，没在月考后花一个半小时手动数错题。

所以这节课的任务不是写代码，是**理解用户**。

2026 年 1 月，ChemAI 项目用一种非常规的方式完成了用户调研：角色扮演式访谈。采访者扮演"AI 教研助手"，被访者扮演"寻求帮助的教师"。这不是因为"这个方法更好"，是因为约束条件倒逼的选择——种子教师只有 1 人、每周只能投入不超过 2 小时、焦点小组和问卷都不现实。

三轮访谈下来，我们从一个模糊的"帮老师用 AI"变成了 15 项具体的 JTBD，每项都有用户原话支撑。

你将用 Claude Code 完成同样的过程——模拟访谈、提取 JTBD。PRD 编写将在 Session 6 单独进行，本节课只做一件事：**理解用户**。

```
## 第二部分：信号 vs 噪音识别框架

基于三轮访谈经验，总结 6 条判断标准。每条都要有判断理由和实际例子：

| 类型 | 特征 | 判断理由 | 实例 |
|------|------|---------|------|
| 信号 | ... | ... | ... |
| 噪音 | ... | ... | ... |

框架必须包含这 6 条：
1. 用户主动描述的具体场景 → 信号 / 泛泛的"好用/不好用" → 噪音
2. 用户愿意花时间讨论的问题 → 信号 / "如果...可能..."假设 → 噪音
3. 用户表达了情绪（愤怒/焦虑/疲惫） → 信号 / 礼貌性附和 → 噪音
4. 用户已经尝试过解决方案 → 信号 / 第三方转述的"需求" → 噪音
5. 用户提出具体数据或量化指标 → 信号 / 技术炫技型需求 → 噪音
6. 重复出现 ≥3 次的反馈 → 信号 / 一次性提到的话题 → 噪音

每一条都要从三轮访谈中找一个具体的实例。
```

## 发生了什么（教师参考）

### 1. 为什么用角色扮演而不是问卷？

这个选择不是偏好，是约束倒逼。

| 约束 | 问题 | 如何影响方法选择 |
|------|------|-----------------|
| 时间预算 | 教师每周 ≤2 小时 | 焦点小组需要 2-3 小时连续时间，不可行 |
| 样本量 | 只有 1 位种子教师 | 问卷调查需要 ≥30 样本才有统计意义 |
| 深度要求 | 需要理解教学场景细节 | 问卷只能得到"是/否"答案，无法了解"为什么" |
| 教师性格 | 理性+感性混合，不愿被"调研" | 角色扮演比正式访谈更自然，用户更愿意说真话 |

**关键教训**：一个小样本的用户调研，深度比广度重要得多。1 个人的深度访谈能产出 15 项 JTBD，30 人的问卷可能只有 3 个模糊方向。

### 2. 三轮访谈的核心发现和设计逻辑

**第一轮：不要引导，听用户讲**

第一轮的目的是**发现用户自己认为的最大痛点**。采访者的角色是"AI 教研助手"——不是"产品经理"，不用产品术语。关键技巧：当用户说"这个很烦"的时候，不追问"那你要什么功能"，而是追问"你是怎么做的，一步一步说给我听"。

第一轮的关键原话：
- "每次月考完我要花一个半小时在那数哪道题多少人错"
- "没有人知道我做得多辛苦"
- "第一次用 ChatGPT 出题错了，从此不太信任这类工具"
- "班里十几二十个学生明显跟不上，不是他们不聪明"

这四句话直接决定了后续所有功能的优先级排序。注意："没有人知道我做得多辛苦"这句话不是功能需求——它是一个**情感需求**，说明教师在繁重工作中缺乏认可感。这后来映射到了情感 Job J10（"减少力不从心的疲惫感"）。

**第二轮：聚焦场景，不满足于笼统**

第一轮发现了三个痛点。第二轮的任务是深挖：这些痛点是什么触发的？用户是怎么应对的？应对方案的缺陷是什么？

第二轮的关键发现：
- **10 秒红线**："我扫一道题只需要 10 秒，10 秒内发现明显问题我就放弃整个工具"——这句话决定了 chemical_balance 审核工具必须做到零误报，而不是"尽量少错"
- **三维审核需求**："如果 AI 告诉我这道题考什么、有没有坑、跟哪道真题像，我两分钟扫完就能决定用不用"——这句话决定了审核报告必须是 auditDims 四维结构化报告，不是"通过/不通过"
- **报告分发链**："家长只关心排名和分数，不关心知识点；学生直接发会崩溃，要先过我这一关"——这句话决定了错题报告必须分学生版/家长版两套模板

**第三轮：验证假设，不验证功能**

第三轮的核心方法论是"教练点评"——我把我的理解复述给你，你告诉我哪里理解错了。这不是让用户提需求（用户不会），是验证产品经理的理解是否准确。

第三轮的关键发现：
- **信任脆弱性**："如果我花了时间学怎么用它，结果它还是经常出问题，我会觉得我的时间被浪费了"——这意味着产品不是"好不好用"的问题，是"值不值得学"的问题。学习成本是教师的核心考量
- **维护产品 = 维护判断**："维护产品就是维护我自己的判断"——如果教师推荐了一个工具，结果工具出错了，那教师本人的专业判断力也会受到质疑
- **推荐周期 3 个月**："推荐给同事需要产品稳定运行超过 3 个月"——口碑传播不是即时的，有至少 3 个月的安全验证期
- **付费意愿**："月付 50 到 100 块我可以接受，一年六七百吧。参照那个 128 一年的题库"——定价锚点是竞品题库 APP 的 128 元/年

### 3. JTBD 框架的实践要点

**为什么是 JTBD 而不是 User Story？**

User Story 适合功能已经明确的场景（"作为教师，我希望能导出 Excel 报告"）。但在需求发现阶段，用户自己都不知道要什么功能。JTBD 问的是"你要完成什么工作"而不是"你要什么功能"——前者是开放的，后者是封闭的。

**功能 Job vs 社交 Job vs 情感 Job 的区分**

这是 JTBD 的核心洞察：用户买一个产品，不是为了功能，是为了完成工作（功能 Job）、塑造身份（社交 Job）、满足情感（情感 Job）。

举两个实际例子：
- 教师说"我要错题统计"——这是功能 Job（J1）
- 教师说"如果同事知道我用 AI 辅助教学，会觉得我跟得上时代"——这是社交 Job（J8）
- 教师说"如果我花了时间学怎么用，结果它还经常出问题，我会觉得时间被浪费了"——这是情感 Job（J12）

功能 Job 可以用代码解决。社交 Job 和情感 Job 需要产品设计解决——比如"维护产品就是维护我自己的判断"这句话，决定了 chemical_balance 审核工具必须显示为"AI 审核建议"而非"AI 自动判断"，最终决定权在教师手中。

**15 项 JTBD 的完整矩阵**（来自三轮访谈的实际提取）：

功能 Job（7 项）：
| # | Job | 用户原话 | 当前方案 | 耗时 | 优先级 |
|---|-----|---------|---------|------|--------|
| J1 | 考试后获得班级错题分布统计 | "每次月考完花一个半小时数哪道题多少人错" | Excel 手动统计 | 1-1.5h/次 | P0 |
| J2 | 快速完成 AI 题目安全审核 | "我扫一道题只需要 10 秒" | 自己重做全部题目 | 30min/次 | P0 |
| J3 | 获得三维分析报告 | "如果 AI 告诉我都考什么、有没有坑" | 凭经验判断 | — | P1 |
| J4 | 生成定制化错题报告 | "发送给家长要重新组织语言" | 手动改写三份 | 20min/次 | P1 |
| J5 | 提供虚拟化学实验 | "有些实验学校做不了，只能讲" | 静态图片 or 放弃 | — | P2 |
| J6 | 识别学生真实障碍类型 | "分数差不多的两个学生，可能一个属于第二类一个属于第三类" | 凭感觉 | — | P1 |
| J7 | 推送自适应练习 | "没办法给每个学生出不同的题" | 统一布置 | — | P1 |

社交 Job（2 项）：
| # | Job | 驱动力量 |
|---|-----|---------|
| J8 | 成为"善用工具"的专业形象 | 被同事认可为与时俱进 |
| J9 | 通过推荐工具维护判断力 | 推荐工具 = 推荐自己的判断 |

情感 Job（3 项）：
| # | Job | 驱动力量 |
|---|-----|---------|
| J10 | 给予 90+ 人班级个性化关注 | 减少"力不从心"的疲惫感 |
| J11 | 不在学生面前失去专业权威 | 保护专业尊严 |
| J12 | 不因学习工具感到时间被浪费 | 学习成本 < 实际节省时间 |

### 4. 信号 vs 噪音：三个实际应用案例的深度解析

**案例 1：从"AI 出题别出错"到 chemical_balance 审核工具**

- 原始需求（噪音形式）："老师，能不能让 AI 出题的时候别出错？"——这是一个不可能完成的需求。没有任何 AI 能做到 100% 准确率。
- 信号提炼："教师每次使用 AI 出题后，需要花 30 分钟自己重新做一遍全部题目来验证正确性——这不是研发愿意接受的用户体验"
- 关键洞察：教师不是要 AI 不出错，是要 AI 出错时能快速发现。需求从"提高准确率"转向了"降低验证成本"
- 功能转化：`app/services/chemical_balance.py` 的 `audit_chemical_equation` 函数，基于价态规则和反应条件数据库，对每道 AI 生成的题目做四维审核（系数/条件/产物/结构）
- 为什么不直接用 LLM 审核：LLM 审核有同样的问题——谁审核审核者？所以 chemical_balance 走规则引擎而非 LLM。规则引擎不依赖概率，对化学方程式配平的核验是确定性的

**案例 2：从"学生跟不上"到 barrier_type 三维诊断**

- 原始需求："班里十几二十个学生明显跟不上，不是他们不聪明"
- 信号提炼：教师能凭经验区分"跟不上"的不同原因，但 90+ 人班额让她无法逐个分析——需要的是一个能自动分类的工具
- 关键洞察（第三轮访谈）："分数差不多的两个学生，可能一个属于第二类，一个属于第三类"——这句话表明，障碍诊断不能依赖分数排名，必须依赖错误模式分析
- 功能转化：`agent/tools.py:diagnose_barrier()` + `students.barrier_type` JSON 字段（`{concept: 0.3, reading: 0.5, expression: 0.2}`）
- 三个维度的区分逻辑：
  - concept：学生在同一知识点的题目反复出错 → 概念没懂
  - reading：学生在题干较长的题目上出错率高 → 题目没读懂
  - expression：学生在书写类题目（方程式、命名）出错率高 → 懂了但写不对

**案例 3：教导主任变种题需求的识别**

- 原始表达（教师转述）："主任说能不能把历年真题改成不同版本让学生练"
- 信号分析：
  - 需求方是教导主任（非一线教师），需求类型属于行政推动（四级来源）
  - 核心场景是月考/期中考试命题——教师需要多套等价试卷防作弊
  - 技术本质是"保持考查目标不变，替换表层信息"
- 关键洞察：教师听到"变种题"第一反应是抗拒——"AI 又要改我的题目了"。需要四条红线（系数/条件/产物/知识点不变）来建立信任
- 功能方案：`agent/tools.py:generate_questions(variant_source=qid)`，选真题为蓝本 → LLM 生成同构变体 → 四条红线约束 → 教师人工确认等价性

### 5. 调研输出的完整转化链

```
三轮访谈记录（~7500 字）
  → JTBD 提取（15 项，功能 7 + 社交 2 + 情感 3）
    → 需求到功能映射表（8 个功能，每个追溯到 JTBD）
      → 输入到 Session 6 PRD 编写（基于 JTBD 矩阵 + 竞品/可行性分析结果）
```

### 6. 经常出现的问题

**Q：学生说"访谈做得很尴尬，不知道怎么问"**
A：访谈的核心不是"问"，是"听"。最好的访谈问题是"你平时是怎么做的？一步一步说给我听"。当教师开始描述她的真实工作流程时，你只需要追问细节——"这个花多久""最烦的是哪个环节""你试过什么办法解决"。问题越具体，回答越真实。

**Q：学生提取的 JTBD 太模糊，每项都是"提高效率"**
A：JTBD 必须有可验证的使用场景。检查标准：每项 JTBD 能否回答以下四个问题——什么时候触发？谁来做？当前怎么做？期望的结果是什么？如果回答不了，说明还没深入到足够的具体场景。

**Q：信号/噪音框架用了但判断不准**
A：最简单的判断标准："如果这个反馈来自用户的具体经历，是信号。如果来自用户的想象，是噪音。"比如"我每次月考后花一个半小时数错题"是经历（信号），"如果能自动生成所有题目的解析就好了"是想象（噪音，需要进一步验证是否为真实需求）。

### 需求来源的六级分层

```
优先级降序：
一级来源（行为证据）  → 用户观察 + 使用数据
二级来源（表达需求）  → 深度访谈 + 问卷调研
三级来源（推导需求）  → JTBD 分析 + 竞品对标
四级来源（外部驱动）  → 学校行政要求 + 政策变化
五级来源（技术驱动）  → LLM 新能力 + 新开源工具
六级来源（假设驱动）  → 产品团队的直觉假设
```

信任度排序的逻辑：用户说的（二级）不如用户做的（一级）可信。用户做了什么（一级）不如为什么做（三级）有价值。三级来源（JTBD）的价值在于它从行为中推导出用户的深层动机，而用户自己可能都意识不到这些动机。

### PRD 编写（将在 Session 6 进行）

PRD 编写不在本节课范围内。Session 6 会专门教 PRD 的结构分析和 Claude Code 高效撰写方法，届时会基于本节课的 JTBD 矩阵 + Session 4 的竞品分析 + Session 5 的可行性分析，综合输出完整的 PRD。

这里先记一个关键教训：

PRD v1.0 曾有一个被删除的功能：**行政上报功能**。这个功能最初是基于"学校需要信息化考核数据"这个外部需求（四级来源）设计的。但在第三轮访谈中，教师明确说"帮我完成行政上报的工具，我第一天就绕过去"。

这个功能被彻底删除而不是推迟——因为做出来用户会绕过去，等于没做。这个决策的教训是：**四级来源（行政需求）需要经过一级来源（用户行为）验证，否则可能是伪需求。**

### 为什么不做学校管理后台

种子教师的付费意愿是个人付费（月付 50-100 元），而不是学校采购。原因：
1. 学校采购流程长（至少一学期），个人付费即时
2. 教师希望工具是自己的，不受学校 IT 部门管控
3. "帮我完成行政上报的工具，我第一天就绕过去"——教师极度排斥被学校监控

这个洞察决定了产品设计方向：教师端优先，学校端可选。不做学校管理后台，不做强制登录对接学校 SSO。
