## 项目背景（给学生的概述）

代码写完了，bug 修完了，性能测完了。但"能用"和"好用"之间还有一个巨大的鸿沟——种子教师验收。

ChemAI 不是内部工具，它要给湖南某重点高中的化学教师实际使用。这位教师教龄 18 年，ChatGPT 出过一次配平错误后就不再信任 AI。让她信任 ChemAI，需要的不是技术演示，而是每个功能都经过她亲手操作的验证。

但验收通过不等于结束。MVP 上线后，3 月中旬教务主任通过种子教师转达了一个新需求："能不能把历年真题改成不同版本让学生练？"优先级瞬间从 P2 跳到 P1——行政力量推动，不是你能拒绝的。

这节课你要做两件事：**验证 MVP**（验收 8 个功能 + 6 个 E2E 场景 + 错误注入测试 + 种子教师内测环境）和**处理新需求注入**（需求分析 → POC 验证 → 前端集成 → 技术债务审计 → 交付清单）。最后做一次课程总结——回顾 ChemAI 从 1 月到 3 月的完整旅程。

## 发生了什么（教师参考）

### 1. MVP 的定义——"种子教师真的在用了"

ChemAI 的 MVP 定义不花哨：`python -m uvicorn app.main:app` 无错启动、种子教师通过局域网访问、8 个功能全部经过教师实际操作、无 P0/P1 blocking bug。"实际使用过"是关键词——不是理论上能用。

### 2. 错误注入测试的方法论

化学方程式审核的核心指标不是"正确率"，是 **false negative rate**（有错但被判为正确的比例）。对于化学教育场景，这个值必须是 0——一个配平错误的方程式如果被审核通过，教师失去信任。5 个测试用例覆盖了 4 种典型错误模式：系数不对、产物错误、未配平、正确（验证不产生 false positive）。

### 3. 需求优先级变更——为什么教务主任一句话 P2 变 P1

这不是技术决策，是组织决策。教务主任是"考试管理者"，他的需求（多套等价试卷防作弊）在教师眼中不是第一优先级，但行政力量推动时优先级必须调整。真实产品的优先级不是产品经理定的——要学会判断"需求背后的权力结构"。

### 4. 四条红线的合理性

| 红线 | 为什么不能破 | 破了会怎样 |
|------|------------|-----------|
| 系数不变 | 系数变了就是不同反应 | 变种题不等价 |
| 条件不变 | 加热/催化剂改变反应类型 | 考查知识点变了 |
| 产物不变 | NaCl vs KCl 离子反应完全不同 | 学生被误导 |
| 知识点不变 | 氧化还原变离子反应——不同章节 | 出题失去公平性 |

### 5. 技术债务不是"代码写错了"

技术债务是"在有限资源和时间内做了最优选择，但留下了已知的局限性"。每一项债务都是在"现在修"和"以后修"之间的权衡。有些债务（如 MinerU 15min/卷）在用户量 <10 时不需要修。

### 6. "新需求 = 旧模块的新参数组合"

ChemAI 迭代的核心理念：变种题没有新建 `VariantGenerator` 类——它只是 `generate_questions(variant_source=exam_id)` 的一个参数。好的架构让新需求变成已有模块的参数组合，而不是新建模块。

### 7. 课程结束语

17 节课，你从 `mkdir chemai-backend` 开始，经历了一个完整的产品生命周期：用户调研（S3）→ 竞品分析（S4）→ 可行性论证（S5）→ PRD 编写与计划（S6）→ 原型设计（S7）→ 数据库设计（S10）→ OCR 管线（S11）→ 前端页面（S12）→ Agent 架构（S13）→ 出题工作台（S14）→ 数据闭环（S15）→ 测试调优（S16）→ MVP 上线与迭代交付（S17）。

ChemAI 没有云服务器、没有 Docker、没有 K8s。它只是一台 Windows 笔记本上跑的 FastAPI + SQLite。但种子教师省下了每周 1.5 小时的错题统计时间，教务主任得到了多套等价试卷的自动生成能力。
