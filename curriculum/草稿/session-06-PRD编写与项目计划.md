## 项目背景（给学生的概述）

前 5 节课你做了很多分析——用户调研、竞品扫描、Kano 分类、RICE 评分、可行性论证。这些分析不是"做了就完了"的作业——它们是你写 PRD 的原材料。

这节课你要做两件事：**写出 PRD** 和 **制定项目计划**。

写 PRD 不是"打开空白文档开始敲字"。有一个现成的参照物——`PRD-智辅化学-Agent产品需求文档.md`，这是一份 1083 行的完整 PRD，覆盖了 26 个功能模块、13 种失败模式、673 条评测标准。你要先读懂它——不是欣赏它写了多少字，是理解它**为什么要这样组织**、**每个章节在回答什么问题**、**哪个章节对后续开发最重要**。

读懂之后，你再用 Claude Code 高效写出自己的 PRD——不是一行行手敲，是告诉 Claude Code 你需要什么内容、什么结构、什么约束，让它帮你生成。

PRD 写完后做项目计划：WBS 把 PRD 拆成可执行的任务树，甘特图把任务排到时间线上。这样 Session 8 开始写代码时，你不用再想"今天做什么"——甘特图已经告诉你了。

## PRD 结构

请按照以下结构撰写。每个章节的要求已标注。

### 1. 执行摘要（≤1 页）
- 产品一句话定义
- 目标用户
- 核心价值主张（1-3 句话）
- 关键指标（3-5 个可量化目标）

### 2. 问题陈述
- 3 个核心痛点，每个包含：
  - 问题描述
  - 用户原话（引用三份访谈记录）
  - 当前替代方案及其缺陷
  - 不解决的代价

### 3. 用户画像
- 种子教师完整画像表（数据来自 Session 3）
- 次级用户画像（学生、家长、教务主任）—— 如有数据支撑就写，没有就标注"待验证"

### 4. 市场与竞品
- 竞品四象限定位（来自 Session 4）
- 差异化总结（至少 3 条 ChemAI 不可替代的优势）
- 市场规模摘要（TAM/SAM/SOM 关键数字，来自 Session 5）

### 5. 功能设计
- 按 RICE 排序列出 MVP 功能（4-6 个）
- 每个功能包含：
  - 功能名称和一句话描述
  - 映射的 JTBD 编号
  - 用户场景（When/Who/What）
  - 验收标准（可测试的、具体的）
  - 优先级（P0/P1/P2）
- 明确标注哪些功能是 MVP、哪些是后续版本

### 6. 产品原则与约束
- 产品原则（3-5 条不可妥协的规则，来自 MVE 的"底线体验"）
- 行为约束（如"化学方程式系数配平必须零错误"）
- 明确不做的事情（基于 Kano 反向型/无差异型的分析）

### 7. 风险评估与缓解
- TOP 5 风险（来自 Session 5 风险矩阵）
- 每个风险的缓解措施和触发条件

### 8. 商业模式
- 定价策略（来自 Session 3 访谈 + Session 5 ROI）
- 目标付费转化路径

### 9. 成功标准
- 可量化的成功指标（模型质量、产品体验、系统性能、成本控制）
- 每个指标的衡量方式

### 10. 路线图
- MVP（当前）→ V1.0 → V2.0 的功能演进
- 粗略时间线（来自 WBS 和甘特图）

## 写作准则

写 PRD 时请遵守以下准则（来自步骤 1 的结构分析）：

1. **每个功能追溯到用户原话或 JTBD**：不能说"应该做 X"，要说"因为教师在访谈中说 Y，所以做 X"
2. **数字必须有来源**：不能说"市场很大"，要说"TAM 约 X 万，计算逻辑见 Session 5"
3. **约束写在功能之前**：先说"这个产品绝对不做什么"，再说"那它做什么"
4. **验收标准可测试**：不能写"用户体验好"，要写"教师完成一次错题统计的时间 < 3 分钟"
5. **边界比功能更重要**：明确说"这个版本不做 X"，比列出 20 个功能更有价值

### 步骤 3：WBS 任务分解

**目标**：将 PRD 中的功能拆解为可执行的 WBS 任务树

**提示词**（复制到 Claude Code）：

```
读取 docs/prd-v1.0.md，将 MVP 功能拆解为 WBS（Work Breakdown Structure）任务树。输出到 docs/wbs-task-tree.md。

## WBS 拆解规则

1. **3 级深度**：
   - 第 1 级：功能模块（对应 PRD 的核心功能）
   - 第 2 级：子任务（每个功能的主要工作项）
   - 第 3 级：叶子任务（可分配给一个人、在一个时间段内完成的具体任务）

2. **叶子任务标准**：
   - 可以在 0.5-2 天内完成
   - 有明确的完成标准
   - 不依赖其他叶子任务内部的工作（依赖关系在 WBS 层级之间体现）

3. **每个叶子任务必须包含**：
   - 任务名称
   - 预估工时（小时）
   - 前置依赖（如果有）
   - 产出物/完成标准

## WBS 覆盖范围

基于 ChemAI 的 MVP 功能（按 RICE 排序），至少拆解以下模块：
1. 错题统计面板
2. AI 出题 + 安全审核
3. OCR 试卷识别
4. 障碍类型诊断
5. 前端页面（教师端 + 学生端）
6. Agent 架构
7. 测试和部署

对每个模块做 3 级拆解，确保叶子任务总数 ≥ 30 个。

## 输出格式

```
## 模块 1：错题统计面板
### 1.1 数据库设计
  - [ ] 1.1.1 设计 student_answers 表结构（2h）→ 产出：DDL 脚本
  - [ ] 1.1.2 设计错题统计聚合查询（1.5h）→ 依赖：1.1.1 → 产出：SQL 视图
  ...
### 1.2 API 开发
  - [ ] 1.2.1 ...
...
```

最后统计：总叶子任务数 ____、总预估工时 ____ 小时、关键路径上的任务 ____ 个。
```

## 发生了什么（教师参考）

### 1. 为什么先分析参考 PRD 再写自己的 PRD？

学生常见错误：打开空白文档就开始写 PRD，写着写着发现结构混乱、前后矛盾。先分析一份成熟的 PRD，能帮学生在动手前建立一个"好 PRD 长什么样"的心智模型。

参考 PRD（`PRD-智辅化学-Agent产品需求文档.md`）有几个特别值得学生关注的特点：
- **行为约束章节**：不是所有 PRD 都有这个，但 ChemAI 必须有——因为教师的信任建立在"不出错"上
- **失败模式目录**：13 种失败模式，每种有概率、影响、缓解——这是"防御性产品设计"的思维
- **评估阈值**：673 条评测标准——把"产品好用"翻译为可测量的指标

### 2. Claude Code 写 PRD 的高效方式

不要一行行手敲 PRD。正确的方式是：
1. 把前 5 节课的分析文档作为输入材料告诉 Claude Code
2. 明确 PRD 的结构要求（10 个章节）
3. 给 Claude Code 5 条写作准则（来自步骤 1 的分析）
4. 让 Claude Code 生成第一稿
5. 你审核、修改、补充——重点是"审"不是"写"

高效的 PRD 写作 = 提供充足的上下文 + 明确的结构约束 + 人审核决策。Claude Code 负责文字生成，你负责判断"这个功能该不该做"。

### 3. WBS 的常见错误

- **叶子任务太大**："搭建 Agent 架构"不是叶子任务，它应该拆成"编写 Gateway 路由"、"实现 Coordinator 节点"、"编写 6 个子专家"等
- **叶子任务太小**："创建 models.py 文件"——这不是任务，这是 30 秒的操作
- **忘记依赖关系**：OCR 管线需要先下载模型才能测试，Agent 需要先有 API 才能集成——这些依赖不标出来，甘特图就是错的
- **没有缓冲时间**：单人开发不能排满 25 小时/周，要留 15-20% 缓冲

### 4. 甘特图不是"排好了就不改"

ChemAI 实际开发中，甘特图至少调整了 3 次：
- 第一次调整：MinerU 模型下载花了 3 天而不是预期的半天
- 第二次调整：前端比预期快了 40%（Vue 3 CDN 方案真的很省时间）
- 第三次调整：种子教师验收后的修复行动打乱了原计划

甘特图的价值不在于"严格遵守"，在于"当偏离计划时，你知道偏离了多少，以及为什么偏离"。项目管理的核心不是预测未来，是偏差可见。

### 5. 经常出现的问题

**Q：学生写的 PRD 是"功能清单"而不是"产品文档"**
A：检查方法：随机挑一个功能，看它有没有回答这四个问题——为什么做（用户证据）？做成什么样（验收标准）？有什么风险？不做会怎样？如果只回答了"做什么"，那就是功能清单。

**Q：WBS 任务太多（80+）或太少（10-）**
A：太少说明拆解不够——"写前端"不是一个叶子任务。太多说明太碎——"创建 index.html 文件"不需要单独列。合理范围 30-50 个叶子任务。

**Q：甘特图全串行——所有任务一个接一个**
A：找可以并行的任务。典型可并行组合：后端 API 开发 + 前端页面开发（只要 API 接口定义好了就可以并行）；LLM 接入 + 数据库设计（无依赖）。单人开发不等于不能并行——你可以上午做 A 下午做 B。
