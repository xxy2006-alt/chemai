## 项目背景（给学生的概述）

PRD 写好了，WBS 拆好了，甘特图画好了——你觉得可以开始写代码了？等一下。在写下第一行正式前端代码之前，先用最低成本验证一下你的设计思路对不对。

原型不是"画线框图"。Prototype 是 Hypothesis——你对"用户会怎么用这个产品"的假设。认知走查是 Experiment——你找一个人按你的假设走一遍，看你的假设是否成立。

ChemAI 的实际开发中，这个环节被跳过了——前端是直接用 Vue 3 CDN 写的。现在回头看，如果一开始先做一个 HTML 原型让种子教师过一遍，至少能提前发现 3 个问题：学生端应该叫"待复习"而不是"错题本"（用户心理抗拒）、出题工作台 4 Tab 的切换逻辑不合理、化学式渲染在移动端的体验问题。

这节课你要用 Claude Code 快速生成可交互的 HTML 原型，然后用认知走查方法验证它。原型不需要漂亮，不需要完整——它只需要能让你在写正式代码之前发现设计问题。

### 步骤 3：创建可交互 HTML 原型

**目标**：用 Claude Code 生成可交互的 HTML 原型页面

**提示词**（复制到 Claude Code）：

```
基于 docs/information-architecture.md 和 docs/user-flow.md，为 ChemAI 创建可交互的 HTML 原型。

## 原型范围

创建以下页面（用纯 HTML + 内联 CSS + 少量 JS 做交互）：

### 教师端（桌面宽屏，≥1200px）
1. **登录页** — 账号密码输入，登录按钮
2. **首页/工作台** — 班级概览卡片（3 个班），最近考试入口，快捷操作按钮
3. **考试工作台** — 4 Tab 切换（试卷管理/出题/错题统计/学情诊断），Tab 切换有内容变化

### 学生端（手机宽屏，375-414px）
4. **首页** — 今日任务列表，待复习提醒
5. **练习页** — 一道化学选择题 + 选项按钮 + 提交后显示对错

## 原型要求

1. **不需要真实数据**：用假数据（"高三（1）班 45 人""氧化还原反应 23 人答错"）填充
2. **不需要真实 API**：点击按钮用 alert() 或简单的 DOM 操作模拟交互
3. **可以丑但不能乱**：灰色背景 + 白色卡片 + 基础文字排版即可，不需要颜色设计
4. **可交互**：用户能在页面之间跳转（用 `<a>` 链接），能在 Tab 之间切换，能点击按钮看到反馈
5. **所有页面放在 frontend/prototype/ 目录下**，首页命名为 index.html

## 技术约束

- 纯 HTML + 内联 CSS（`<style>` 标签），不要外部 CSS 文件
- 不要任何框架（不要 Vue/React/Bootstrap CDN）
- JS 只用原生写法，做 Tab 切换和简单的点击交互
- 教师端页面宽度固定为 1200px 居中，学生端页面宽度固定为 375px 居中
- 教师端和学生端用不同目录：frontend/prototype/teacher/ 和 frontend/prototype/student/
- 学生端页面用 `<meta name="viewport" content="width=375">` 模拟手机宽度

## 交互细节

- 教师端考试工作台：4 个 Tab 点击切换内容
- 学生端练习页：点击选项 → 显示"✓ 正确"或"✗ 错误" → 显示解析
- 登录页：输入任意内容 → 点击登录 → 跳转到首页

先创建目录结构，再逐个创建文件。
```

### 步骤 4：认知走查

**目标**：用 Nielsen Norman Group 的认知走查方法，对原型进行可用性评估

**提示词**（复制到 Claude Code）：

```
用认知走查（Cognitive Walkthrough）方法评估你刚创建的 ChemAI 原型。输出到 docs/cognitive-walkthrough.md。

## 认知走查方法（NN/g 标准）

对每个用户步骤，问四个问题：
1. **用户会尝试做正确的事吗？** — 用户看到这个页面，会知道要做什么吗？
2. **用户能找到正确的操作吗？** — 按钮/链接/入口是否可见、可理解？
3. **用户能把操作和结果关联起来吗？** — 点击后用户能理解发生了什么吗？
4. **用户能确认进展吗？** — 系统反馈是否让用户知道"做对了"？

## 三个走查场景

### 场景 1：教师首次登录 → 查看班级概览
走查步骤：
1. 打开登录页 → 输入账号密码 → 点击登录
2. 看到首页 → 理解页面布局
3. 找到班级概览 → 理解卡片信息

### 场景 2：教师出题 → 审核 → 保存
走查步骤：
1. 进入考试工作台 → 找到出题 Tab
2. 理解出题界面 → 发起出题
3. 看到审核结果 → 确认或修改
4. 保存到题库

### 场景 3：学生做练习 → 看到反馈
走查步骤：
1. 学生打开练习页 → 理解题目
2. 选择答案 → 提交
3. 看到对错反馈 → 理解解析
4. 进入下一题

## 输出格式

对每个场景，用表格呈现走查结果：

| 步骤 | 问题 1 | 问题 2 | 问题 3 | 问题 4 | 严重程度 | 改进建议 |
|------|--------|--------|--------|--------|---------|---------|
| ... | 通过/问题 | 通过/问题 | 通过/问题 | 通过/问题 | 高/中/低 | ... |

## 严重程度定义
- 🔴 高：用户完不成任务（阻断性）
- 🟡 中：用户能完成任务但有困惑/挫折
- 🟢 低：小的体验瑕疵

## 总结

- 共发现 ____ 个问题（高 ____ / 中 ____ / 低 ____）
- 必须在写正式前端代码前修复的 TOP 3 问题
- 对原型设计的整体评价
```

## 发生了什么（教师参考）

### 1. 为什么用 HTML 原型而不是 Figma？

Figma 做出来的原型"看起来像真的但不能用"。HTML 原型"看起来不像真的但能用"——后者对验证交互逻辑更有价值。教师在 Figma 里看到一个 4 Tab 切换的设计会觉得"哦这个好"，但在 HTML 原型里点几下 Tab 发现"怎么切了 tab 之前填的内容没了"——这个问题 Figma 发现不了。

另外，用 Claude Code 生成 HTML 原型只需要复制粘贴提示词，比学 Figma 快得多。对非设计背景的学生来说，HTML 原型是效率最高的原型工具。

### 2. 认知走查 vs 用户测试

- 用户测试：找真实用户试你的产品，看他们怎么用
- 认知走查：你自己扮演用户，按 NN/g 四问评估每一步

学生没有真实化学教师可以测试原型——即使有，原型阶段也太早。认知走查是最适合这个阶段的评估方法：不需要用户，能系统性地发现问题，成本为零。

但认知走查有局限性：你无法发现"你自己没意识到的问题"——因为走查者是设计者本人。所以认知走查的结论是"发现问题"的信号，不是"没问题"的证明。

### 3. 学生端"待复习"而非"错题本"的命名教训

ChemAI 学生端最初的导航名称是"错题本"，后来改为"待复习"。这不是设计审美偏好——是认知走查的结论：

- "错题本"暗示"你错了"——学生在打开这个页面之前就有负面情绪
- "待复习"暗示"你需要巩固这些"——中性的学习行为描述
- 用户心理：学生不愿意看"错题本"，但愿意看"待复习"

一个词的差别，影响的是用户的打开率。这就是为什么原型阶段要做认知走查——在写正式代码之前，你改一个词只需要 10 秒。写了代码再改，可能要改数据库字段、API 接口、前端文案。

### 4. 经常出现的问题

**Q：学生做的原型太"高保真"——花了半节课调 CSS 颜色**
A：原型的目的不是好看，是验证交互逻辑。颜色和字体在原型阶段不重要。如果学生花了超过总时间 20% 在视觉细节上，提醒他们：这是原型，不是产品。灰色的方块和白色的按钮就足够了。

**Q：认知走查 4 个问题全写"通过"**
A：没有任何设计是完美的。如果全部通过，要么是走查不够认真，要么是场景太简单。让换一个更复杂的场景重做——比如"教师想修改一道已保存的题目"，或者"学生做练习中途退出后再进来"。
