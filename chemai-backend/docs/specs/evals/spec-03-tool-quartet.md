# Spec 03 — 基础工具四件套：read/write/edit/bash（沙箱）+ find/grep

> 状态：ready-for-agent ｜ Phase：P2（开发 A）｜ 依赖：Spec 01、02 ｜ 被测对象：L0/L3 场景
> 依据：`docs/evals/eval-system-design.md` §7-A（四件套 + L0 评估先行 + L3 同步扩）。

## Problem Statement

Agent 现在完全没有文件与命令能力：`agent/tools/` 里全是业务工具（题库/辅导/诊断），既不能读用户上传的材料文件，也不能把生成物（如试卷）写出来，更不能执行任何命令。设计文档开发路线 A 要求补齐 `read/write/edit/bash` 四件套（bash 沙箱化）+ `find/grep` 辅助，并明确**评估先行**：四件套的 L0 断言（编码/路径穿越/敏感文件拒绝、精确替换/找不到明确报错、沙箱逃逸/危险命令/超时）必须先于实现写成红色，L3 对抗语料（bash 注入、危险命令拦截）同步扩展。这是一个"先写红评估再开发到绿"的完整 eval-first 项目。

## Solution

从用户视角：**老师**可以让 agent 直接读材料文件、把生成的内容写入文件、对文件做精确修改，还能执行受限的命令——所有这些都在工作目录之内、白名单之内、有超时与输出限制，敏感文件与危险命令被拒绝且报错明确。**开发者**看到的是：红评估先落地（`expected_fail` 不挡门禁）→ 逐个工具开发到绿 → 标记移除转常驻门禁。

## User Stories

1. 作为一个老师，我想要 agent 读取我指定的文档文件，这样它能直接基于我的材料分析、出题或批改。
2. 作为一个老师，我想要 agent 把生成的内容（如出好的试卷）写入文件，这样我能拿到可下载、可留存的产物。
3. 作为一个老师，我想要 agent 精确修改文件的指定片段（替换唯一匹配的原文），这样修改不会误伤其他内容。
4. 作为一个老师，我想要 edit 在找不到目标片段时给出明确报错（含上下文定位），这样我能立刻知道修改没有发生、文件未被破坏。
5. 作为一个用户，我想要 agent 拒绝读取敏感文件（配置、密钥、.env 等），这样我的凭据不会经 agent 外泄。
6. 作为一个用户，我想要 agent 的文件访问被限制在指定工作目录内（含 `..` 穿越与绝对路径拒绝），这样它碰不到工作目录以外的任何文件。
7. 作为一个用户，我想要 agent 的 bash 只允许白名单命令，这样危险命令（删库、下载执行等）根本到不了系统。
8. 作为一个用户，我想要 bash 有超时与输出截断，这样挂起的命令或海量输出不会拖垮整个 agent。
9. 作为一个开发者，我想要四件套的 L0 测试**先于实现**写成红色（`expected_fail`），这样"什么算对"在动手前就被钉死。
10. 作为一个安全评审者，我想要 L3 对抗用例覆盖路径穿越、编码绕过、命令注入（`;`、`&&`、`$()`、重定向）与沙箱逃逸，这样沙箱是被测出来的，不是被假设出来的。
11. 作为一个开发者，我想要四件套在 Windows 开发机与 ubuntu CI 上行为一致，这样本地结论与 CI 结论不打架。
12. 作为一个维护者，我想要 find/grep 只在工作目录内搜索，这样搜索不会外溢也不会泄密。
13. 作为一个老师，我想要读文件时编码错误有兜底与明确提示，这样打开 GBK/UTF-8 混用的中文材料不会莫名其妙失败。
14. 作为一个维护者，我想要新工具进入 `TOOLS` 注册表后 CI 的工具数断言同步更新，这样注册遗漏会被 CI 抓住。

## Implementation Decisions

1. **新模块**：`agent/tools/filesystem.py`（read/write/edit/find/grep）+ `agent/tools/shell.py`（bash），沿用现有工具风格（docstring 供 v2 agent 工具选择、`TOOLS`/`TOOL_META` 注册）。六工具注册后 `ci.yml` imports job 的 `assert len(TOOLS) == 26` 更新为实际新数字。
2. **沙箱形态（本 spec 定为进程级）**：工作目录锚定（路径规范化 + 包含性校验，拒绝绝对路径逃逸与 `..` 穿越）+ 命令白名单（Windows/ubuntu 各一套安全集合，如 `ls/dir`、`find`、`grep`、`python`、`git status` 等）+ 超时（默认 30s）+ 输出截断（默认 8KB）+ `subprocess` 列表参数调用（**不用** `shell=True`，从机制上消除注入面）。**容器级沙箱明确不做**，留待后续立项。
3. **敏感文件拒绝**：拒绝名单模式（配置、密钥、`.env`、证书类路径/内容特征）+ 路径穿越检查；二进制/不可解码文件报明确错误而非输出乱码。
4. **edit 语义**：精确替换——`old_string` 必须且只能唯一匹配一次，否则报错并给出匹配次数与上下文；写入前不改变原文件（先读后写，替换失败零副作用）。
5. **eval-first 时序（与 Spec 01 的 `expected_fail` 机制配合）**：第一步——四件套全部 L0 红测试 + L3 对抗用例入库，全部标 `expected_fail`；第二步——逐工具开发到绿；第三步——逐工具移除标记转常驻。红→绿的过程本身即开发进度指标。
6. **L3 同步扩**：在既有安全测试（isolation）旁新增对抗语料：bash 注入（`ls; rm -rf /`、`$(whoami)`、重定向写敏感路径）、危险命令拦截、跨目录访问、超时行为。设计文档要求 L3 与 A 同步，本 spec 一起交付。
7. **平台策略**：命令执行层做平台适配（Windows 走 cmd/PowerShell 路径、ubuntu 走 bash），白名单各自维护；L0/L3 测试在双平台可跑（CI 跑 ubuntu，Windows 本地跑同一套）。
8. **不改既有业务工具**：本 spec 只新增文件/命令能力，26 个业务工具行为零改动（surgical）。

## Testing Decisions

- **红评估先写**：`evals/test_filesystem_tools.py` + `evals/test_shell_tools.py` 先落（全部 `expected_fail`），再实现工具；测试只断言外部行为（读到的内容、拒绝时报错消息、逃逸被拦、超时被切），不断言实现细节。
- **确定性、零 LLM**：全部用例纯标准库，进快跑层、CI 必跑。
- **Prior art**：`test_unit_tools.py`（纯逻辑断言风格）、`test_safety_isolation.py`（L3 对抗风格）。
- **跨平台验收**：CI（ubuntu）deterministic job 全绿 + 本地 Windows 跑同一套全绿。
- **验收命令**：
  1. 红阶段：`python evals/run_evals.py --fast` 全绿退出 0（红测试被 expected_fail 豁免），报告中红测试以 pending 可见；
  2. 完成阶段：红测试逐个转绿、标记移除，`--fast` 仍退出 0；
  3. 注入对抗回归：手动跑一条危险命令（如 `rm -rf`）被拒绝且报错明确；
  4. CI imports job 工具数断言更新后通过。

## Out of Scope

- 容器级/更强隔离沙箱（后续另行立项）
- 文件工具的"用户上传文件会话绑定"产品化（本 spec 只交付工作目录内通用能力，与既有 `/api/agent/upload` 的衔接如需要另立 spec）
- L2 判官（Spec 04）、出题智能化（Spec 05）、planner 与 L6（Spec 06）
- 白名单的图形化配置界面（白名单先以代码内清单维护）

## Further Notes

- 本 spec 是设计文档 §7-A 的完整落地，也是"评估先行"工作流的第一次实战：红→绿的节奏会验证 Spec 01 的 `expected_fail` 机制是否顺手。
- 危险命令清单与白名单是本 spec 的安全核心，实现时以"默认拒绝、白名单放行"为原则，绝不"默认放行、黑名单拦截"。
- Windows 上 bash 工具的语义（用 cmd 还是 PowerShell）在实现时以"最接近白名单可约束"为准选择，并在 spec 实现说明中记录选择理由。
