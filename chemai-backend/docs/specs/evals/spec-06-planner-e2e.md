# Spec 06 — planner 接线 + L6 端到端场景

> 状态：ready-for-agent ｜ Phase：P5（开发 C）｜ 依赖：Spec 05 ｜ 被测对象：L2「拆解与进度」+ L6 场景
> 依据：`docs/evals/eval-system-design.md` §7-C（planner 零引用死代码、拆解与进度场景先行、前端步骤 UI）、§2 L6。

## Problem Statement

两件事叠加：其一，`agent/planner.py`（147 行，Plan/PlanStep/PlanGenerator + JSON 步骤协议）是零引用的死代码——复杂任务（如"出一套卷子、给全班诊断、出干预方案"）没有步骤计划，用户看不到进度，长任务体验像卡死；其二，七层模型最顶层 L6 端到端完全空白——没有任何"完整任务成功率"的度量。设计文档开发路线 C 要求：L2「拆解与进度」场景先行 → planner 接入 v2 agent → 前端步骤 UI；L6 场景剧本 + 成功判定同步建立。

## Solution

从用户视角：**老师**给一个复杂任务时，agent 会先产出步骤计划、执行中逐步汇报进度、前端有步骤进度 UI 可看；**发布负责人**在慢跑层拿到端到端任务成功率（如"出题→保存→批改"全链路），端到端失败参与一票否决。

## User Stories

1. 作为一个老师，我想要 agent 接到复杂任务时先拆解出步骤计划，这样我知道它要做什么、按什么顺序做。
2. 作为一个老师，我想要 agent 在执行中按步骤汇报进度，这样长任务不显得卡死、我可以中途纠偏。
3. 作为一个老师，我想要前端有一个步骤进度视图（进行中/完成/失败），这样进度一目了然。
4. 作为一个测试者，我想要「拆解与进度」golden 场景先写成红色，这样"什么叫好的任务拆解"在开发前被钉死。
5. 作为一个开发者，我想要 planner 接进 v2 agent 后场景转绿，这样红→绿即开发进度。
6. 作为一个发布负责人，我想要首批端到端场景（出题→保存→批改全链路）带成功判定，这样完整任务成功率可度量。
7. 作为一个发布负责人，我想要 L6 端到端失败参与一票否决，这样"链路走不通"能拦下发布。
8. 作为一个产品负责人，我想要端到端成功率进趋势库，这样任务级质量趋势可见。
9. 作为一个开发者，我想要 planner 的步骤协议复用现有 JSON 协议（depends_on、状态机 pending/running/completed/failed/skipped），这样死代码不用重写协议、只做接线。
10. 作为一个老师，我想要简单任务不强制出计划，这样闲聊与单步操作不被计划拖累。
11. 作为一个维护者，我想要 L6 场景跑在慢跑层（不进快跑），这样快跑门禁不被长链路拖慢。

## Implementation Decisions

1. **场景先行（红）**：golden yaml 新增「拆解与进度」场景组（`expected_fail`）：复杂任务 → 产出 ≥2 步计划且步骤在 SSE/状态中可见；执行中 → 步骤状态随进度更新；简单任务 → 零计划（反例，防过度拆解）。
2. **planner 接线**：把 `agent/planner.py` 的 `PlanGenerator` 接入 v2 agent 的复杂任务路径——沿用其既有 JSON 步骤协议（step/skill/args/depends_on/status 状态机，代码原样复用，不重写协议）；`Plan` 状态挂入 per-invocation 共享状态（GuardState 同款思路），通过 v2 SSE 通道向事件流推送 plan/step 事件。
3. **前端步骤 UI**：前端新增步骤进度组件，消费 SSE 的 plan/step 事件渲染进行中/完成/失败；这是本 spec 唯一的前端改动。
4. **L6 场景剧本**：首批 2-3 条端到端剧本（如：出 5 道题→保存到题库→选题组成试卷→批改答题卡→出诊断），每条含前置数据、输入序列、**成功判定**（终点状态断言：题库可搜到题、批改记录已写库等）。跑在慢跑层。
5. **门禁关系**：L6 端到端失败 = severe → 一票否决（Spec 01 机制）；「拆解与进度」L2 打分只进趋势。
6. **改动边界**：planner 协议不重写；v2 agent 架构不变，只加计划分支与事件推送；业务工具不改。

## Testing Decisions

- **L1 轨迹断言**：复杂任务调计划路径、步骤事件出现在 SSE 流、状态转移正确；反例（简单任务零计划）从第一天必须绿。
- **L6 成功判定测外部终点状态**（数据落库、可被搜索/查询），不测中间过程——先例参照 `agent_eval_golden.yaml` 的 workflow_scenarios 与 `test_regression_complete.py` 的端点级断言风格。
- **L6 在慢跑层**：需 API + 数据准备，CI 不自动跑；发布前手动触发。
- **验收命令**：
  1. 红阶段 `--fast` 绿（expected_fail 豁免）；反例场景开发前后都绿；
  2. 接线完成：`--golden` 下「拆解与进度」场景全绿、标记移除；
  3. SSE 流中出现 plan/step 事件（手动一次复杂任务验证）；
  4. 前端步骤组件渲染进行中→完成的完整状态（手动验证）；
  5. 慢跑层跑通首批 L6 剧本，成功判定输出 + 失败时 severe 否决生效。

## Out of Scope

- planner 协议本身的升级/重写（沿用现协议；多步并行执行、人工确认步骤等增强另行立项）
- L6 场景的批量扩充（首批 2-3 条验证链路后，后续按能力族滚动补充）
- 其他任何前端改动（除步骤进度组件）
- 端到端场景的自动数据准备工具（首批用手工/脚本准备前置数据）

## Further Notes

- 本 spec 把死代码变为活资产：planner 的 JSON 协议是 openspec agent-planner-layer 的既有产物，接线优先于重写（CLAUDE.md：不重构没坏的东西）。
- 简单任务不拆解是交互红线——计划是手段不是仪式，反例断言保底。
- 前端步骤 UI 与 SSE 事件是本 spec 唯一的跨端改动面，事件 schema 要在实现前与前端对齐（事件名、负载字段）。
- L6 是七层模型的封顶：它的落地意味着评估体系从"测零件"完整走到"测整车"。
