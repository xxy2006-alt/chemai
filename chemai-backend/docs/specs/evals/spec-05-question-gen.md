# Spec 05 — 出题智能化：交互智能场景先行 + persona 增强

> 状态：ready-for-agent ｜ Phase：P4（开发 B）｜ 依赖：Spec 04（judge harness）｜ 被测对象：L2 交互智能族 + L1 golden
> 依据：`docs/evals/eval-system-design.md` §7-B（「我要出题」必须追问 + 按薄弱点推荐）。

## Problem Statement

老师对 agent 说「我要出题」，agent 目前只会机械地打开出题工作台，不追问题型/难度/知识点，也不会根据班级薄弱点推荐——交互智能是空白。设计文档开发路线 B 要求**交互智能 golden 场景先行**：「我要出题」→ 必须追问题型/难度/知识点 + 按班级薄弱点推荐，然后才做 persona/prompt 增强与薄弱点上下文注入的开发。这也是 L2 交互智能族判官的第一批真实校准素材来源（Spec 04 需要它）。

## Solution

从用户视角：**老师**说「我要出题」后，agent 会在**一轮之内**给出题型/难度/知识点选项并基于班级薄弱点主动推荐，而不是机械开面板；行为被 golden 场景钉住（红先行 → 开发到绿 → 常驻回归），同时这批场景喂给 Spec 04 的判官做交互智能族校准。

## User Stories

1. 作为一个老师，我想要说「我要出题」后 agent 主动追问题型、难度、知识点，这样生成的题目才是我真正想要的。
2. 作为一个老师，我想要 agent 在追问时给出选项而不是开放式反问，这样我一轮就能答完、不被反复盘问。
3. 作为一个老师，我想要 agent 结合我班级的薄弱知识点做推荐，这样题目打在学生的真实薄弱点上。
4. 作为一个老师，我想要薄弱的依据可见（如"最近 5 次作业中电离平衡正确率 40%"），这样我信任推荐而不是盲从。
5. 作为一个测试者，我想要以上行为先写成 golden 场景（红、`expected_fail`），这样"什么算好的出题交互"在开发前就被钉死。
6. 作为一个开发者，我想要红场景在 persona/prompt 增强后转绿，这样红→绿节奏就是开发进度。
7. 作为一个判官运营者，我想要这批场景翻译成 L2 交互智能族的校准样本，这样判官有真实"蠢场景"演化来的标注数据。
8. 作为一个发布负责人，我想要这些场景转绿后常驻快/慢跑层，这样出题交互永不静默退化。
9. 作为一个老师，我想要非出题意图的消息不被误追问，这样闲聊与知识问答保持轻量。
10. 作为一个产品负责人，我想要薄弱点上下文注入不改变 agent 在其他能力上的行为，这样 B 的开发不带来回归。

## Implementation Decisions

1. **场景先行（红）**：在 `agent_eval_golden.yaml` 新增交互智能场景组，全部 `expected_fail: true`：
   - 出题意图识别：「我要出题」→ 必须追问（断言：不应直接调 `show_exam_workbench` 或追问消息含题型/难度/知识点三要素）；
   - 选项式追问：追问消息应包含可选选项（断言文本模式：含"题型"+"难度"+"知识点"关键词且给出选项枚举）；
   - 薄弱点推荐：带班级上下文的出题 → agent 输出含薄弱点推荐（断言引用诊断数据字段或推荐文案模式）；
   - 反例：闲聊/知识问答 → 零追问（复用现有 `chat-greeting` 语义，防误伤）。
2. **开发（转绿）**：
   - persona/prompt 增强：在 persona YAML 与系统 prompt 中加入出题交互契约（先追问、给选项、一轮内完成、结合薄弱点）；
   - 薄弱点上下文注入：从诊断数据（班级维度的障碍/错误率聚合）注入 agent 上下文，供推荐引用；注入内容必须带来源可溯（哪个数据字段、哪个时间窗）。
3. **判官校准素材**：把红场景及其预期行为翻译为 Spec 04 校准集格式（交互智能族 20-30 条），与 Spec 04 校准管线对接；该族启用与否按 Spec 04 的 ≥80% 门槛走。
4. **转常驻**：场景转绿后移除 `expected_fail`，交互智能断言进快跑层（L1 轨迹部分）；L2 交互智能族打分进慢跑层趋势。
5. **改动边界**：只动 persona/prompt 与上下文注入层；不改工具实现、不改 v2 agent 架构（surgical）。

## Testing Decisions

- **golden 断言只测外部行为**（调了什么工具、追问消息是否含要素、推荐是否引用薄弱点），不断言 prompt 内部文本。
- **红→绿验收**：红阶段 `--fast` 绿（expected_fail 豁免）；开发后逐场景转绿；反例场景（闲聊不追问）从第一天起就必须绿——防误伤是硬断言。
- **Prior art**：`agent_eval_golden.yaml` 的 workflow_scenarios（"空知识点→必须反问"是同族先例，可参考其断言写法）。
- **验收命令**：
  1. 红阶段：`python evals/run_evals.py --fast` 退出 0，报告可见 pending 场景；
  2. 开发完成：移除标记后 `--fast` 仍退出 0，且新场景断言在 `--golden` 下真实通过（需 API）；
  3. 反例场景在开发前后都绿；
  4. 交互智能族校准样本被 `calibrate.py` 接受并输出一致率。

## Out of Scope

- 判官 harness/校准管线本身（Spec 04）
- 出题工作台 UI 的改动（B 只做 agent 侧智能；面板改造另行立项）
- 薄弱点推荐算法的建模升级（本 spec 只做"注入 + 引用"，算法优化另行立项）
- planner 与 L6（Spec 06）

## Further Notes

- 本 spec 与 Spec 04 是供给关系：场景是判官交互智能族校准集的主要来源，两 spec 的验收互相咬合。
- "蠢场景"翻译是校准集建设的关键动作——从 grilling 会话与真实使用记录里提炼"老师怎么被 agent 气到"的场景，翻译成断言与标注样本；这部分人工工作量大，但不可跳过。
- 追问轮数契约（一轮内给选项）是本 spec 的交互红线：宁可推荐得浅，不可盘问得烦。
