# Spec 04 — L2 判官：五族 rubric + 校准 + 人机兜底

> 状态：ready-for-agent ｜ Phase：P3 ｜ 依赖：Spec 01（可并行于 Spec 02/03）｜ 接缝：judge 入口（3）
> 依据：`docs/evals/eval-system-design.md` §3（判官库）、`docs/adr/0007-agent-eval-system.md`（备选 provider、低置信度人工复核）。

## Problem Statement

ChemAI 目前的评估只能断言"调了哪个工具、参数对不对"，完全没有答案质量与交互质量的度量——agent 出题是否化学正确、判卷是否判对、诊断类型是否判断准、给的方案是否适配、交互是否聪明，全都无人打分。ADR-0007 已否决"维持三分法"，理由正是：没有判官层就无法回答「Agent 聪不聪明」。本 spec 建立 L2 判官层：五族 rubric、备选 provider、校准门槛、人机混合兜底、成本预算。

## Solution

从用户视角：**发布负责人**在慢跑层得到每族能力的分数量表（只进趋势、不拦发布），化学错误等严重问题由判官明确标出参与一票否决；**校准负责人**用每族 20-30 条人工标注样本测量"判官 vs 人工"一致率，≥80% 的族才启用自动打分，不达标的族自动走"判官 + 人工复核"混合模式；**维护者**看到每次慢跑花的判官调用数与钱（单次 ≤200 次调用、约 ¥2-5，月预算 ¥500 内）。

## User Stories

1. 作为一个开发者，我想要一个单一判官入口 `judge(sample, rubric_family) -> {score, confidence, rationale}`，这样所有 L2 场景共用一个契约，换 provider 不换调用方。
2. 作为一个判官运营者，我想要判官用与被评模型不同的 provider，这样避免自评偏差（ADR 否决项）。
3. 作为一个判官运营者，我想要五族 rubric（出题/判卷/诊断/方案/交互智能）各自定义打分维度，这样评分贴合各能力族语义。
4. 作为一个判官运营者，我想要出题族 rubric 中"化学正确性"权重最高，这样格式再漂亮、化学错了也必然低分。
5. 作为一个校准负责人，我想要每族 20-30 条人工标注样本构成校准集，这样判官一致性可以被测量。
6. 作为一个校准负责人，我想要判官与人工一致率 ≥80% 的族才启用自动计分，这样噪声不会混进门禁与趋势。
7. 作为一个校准负责人，我想要启用前先用真题 vs 官方答案实测判官能力（出题/判卷族），这样判官能力是证明出来的，不是假设出来的。
8. 作为一个发布负责人，我想要低置信度（或低分）样本自动抽入人工复核队列，只有判官自信的部分才自动计入，这样兜底始终在。
9. 作为一个维护者，我想要每次慢跑记录判官调用次数与成本（¥），这样月度 ¥500 预算可见可控。
10. 作为一个维护者，我想要单次慢跑判官调用硬上限 200 次，这样一次运行不可能烧穿预算。
11. 作为一个开发者，我想要判官 harness 的测试用 canned LLM 响应（假 provider），这样打分逻辑零成本可测。
12. 作为一个产品负责人，我想要判官分数流入趋势库（Spec 01）而绝不进门禁，这样质量趋势随每次慢跑累积。
13. 作为一个判官运营者，我想要每条判定带 rationale 与 confidence，这样人工复核时有据可查、复核成本低。
14. 作为一个发布负责人，我想要判官明确标记"严重错误"（化学错误/安全问题）的结果参与一票否决，这样慢跑层否决机制（Spec 01）有真实数据来源。

## Implementation Decisions

1. **判官入口（接缝 3）**：`evals/judge.py` 暴露单一函数契约 `judge(sample, rubric_family) -> {score, confidence, rationale, severe_flags}`；provider 抽象成接口，测试注入假 provider，生产用真 provider。所有 L2 调用方只碰这个入口。
2. **Provider 决策（定稿）**：判官用 **deepseek** 作备选 provider（主 agent 为 qwen/mimo，天然错开；CI 已配置 `DEEPSEEK_API_KEY` secret）。配置新增判官专属设置（`JUDGE_PROVIDER/JUDGE_MODEL/JUDGE_API_URL`），默认 deepseek，与主模型配置完全独立。
3. **五族 rubric（设计 §3 落地）**：出题（化学正确性权重最高 + 难度匹配 + 解析正确 + 格式规范）、判卷（每题判分 vs 黄金答案）、诊断（障碍类型 concept/reading/expression）、方案（适配性 + 可执行性 + 个性化）、交互智能（澄清追问、主动推荐、给选项引导、拆解与进度）。分数统一 0-100 + 置信度 low/medium/high 三级。
4. **校准管线**：校准集存放为版本化数据文件；`evals/calibrate.py` 脚本跑判官过校准集 → 输出每族一致率报告（判官 vs 人工，含容差规则）→ 一致率 ≥80% 的族标记"已启用"，未达标族标记"人机混合"（判官必过人工复核）。**启用决定在族粒度，不是全局开关。**
5. **校准数据源（定稿）**：出题/判卷族用题库真题 + 官方答案；诊断/方案族用项目历史诊断数据（`StudentAnswer`/诊断记录中人工已标注的样本）；交互智能族用真实"蠢场景"翻译成的 golden 场景（Spec 05 的红场景先行供给）。数据不足的族先不启用、走人机混合，补齐后再测。
6. **人机兜底（人机混合）**：confidence=low 或分数处于"低分临界区"的样本自动进入复核队列（报告内附样本清单）；仅 high/medium 置信度的自动计分进入趋势；复核结果回写样本库用于下次校准。
7. **成本控制**：单次慢跑判官调用硬上限 200 次（超出即截断并在报告标注"未测样本 N 条"）；成本台账写入 Spec 01 报告 cost 段（调用数 + 按 provider 单价估算 ¥）；月度预算 ¥500 为软约束，报告按月累计提示。
8. **与门禁的关系**：判官分数**永不进门禁**；判官输出的 `severe_flags`（化学错误、安全问题）由慢跑层否决逻辑消费（Spec 01 已定义 severe 一票否决）。

## Testing Decisions

- **harness 逻辑测试（快跑层、零成本）**：用假 provider 返回 canned 响应，测 rubric 解析、分数映射、置信度提取、severe_flags 识别、200 次上限截断、复核队列抽取——全部离线可测。Prior art：无判官先例，测试风格参照 `test_unit_tools.py` 的纯逻辑断言。
- **判官能力实测（慢跑层、真 API）**：启用前跑 `calibrate.py`——出题/判卷族 vs 真题官方答案，输出一致率报告；这是"实测判官能力"的门槛步骤，不进 CI 自动跑（需 API key，由校准负责人手动触发）。
- **校准集自身的测试**：校准样本的 schema 校验（样本数 ≥20/族、标注字段齐全），防脏数据进校准。
- **验收命令**：
  1. `pytest evals/test_judge.py -q`（假 provider）全绿；
  2. `python evals/calibrate.py --family question_gen` 输出一致率报告；
  3. 一致率 ≥80% 的族在注册表中显示"已启用"，其余显示"人机混合"；
  4. 模拟一次慢跑（假 provider）验证 200 次上限与 cost 段写入。

## Out of Scope

- 五族 rubric 之外的判官能力（对话满意度等，后续可扩族）
- 判官 prompt 的自动优化/自举（人工迭代 rubric）
- 复核队列的产品化 UI（本 spec 只出报告内清单；UI 另行立项）
- Spec 05 的交互智能场景内容本身（本 spec 只建 harness 与管线，场景由 Spec 05 供给）
- 慢跑层 CI nightly 接线（在 harness 与校准达标后随本 spec 收尾落地：nightly schedule + 发布前手动触发）

## Further Notes

- 判官一致性 ≥80% 是设计文档的硬门槛：族不达标就人机混合，绝不带病启用——这是本 spec 的第一原则。
- deepseek 作为备选 provider 的默认决定基于"CI 已有 key + 与主模型错开"两个事实；若实测判官能力不足，回退路径是换 provider 重测（接缝 3 保证调用方零改动）。
- 校准集是**版本化资产**（同 golden yaml 待遇），人工标注一次要能被反复复用、复审、增量补充。
